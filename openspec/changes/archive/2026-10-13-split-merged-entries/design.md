# Design

## Context

Объединение живёт в `js/merge.js`: `mergeEntries` складывает строки в одну запись, `splitEntry`
делит запись по позициям. Позиции (`items`) есть у разбора снимка и разговора; у записи из
продукта (`js/products.js:192`) и у ручной записи позиций нет.

Отсюда две беды. Первая: объединение строк без позиций даёт запись с пустым списком позиций,
и разбор у неё недоступен. Вторая: строки при объединении удаляются, поэтому вернуть их нечем.
Окно записи открывается по условию `js/ui/today.js:170`, где тоже спрашиваются позиции, поэтому
у такой записи открывается не окно разбора, а форма правки.

## Goals / Non-Goals

Цель: объединение обратимо, разбор возвращает строки, из которых собран приём пищи.

Не цели:

- Переносить снимок на составляющие при разборе. Порядок остаётся прежним: снимок хранит
  объединённая запись.
- Восстанавливать составляющие у записей, объединённых до этой правки: их в данных нет,
  и восстановить их не из чего. Такие записи разбираются по позициям, как раньше.
- Разбирать запись из одного продукта или из одной позиции.

## Decisions

### Составляющие хранятся в самой записи

Объединённая запись получает поле `parts`: список строк, из которых она собрана. Строка хранится
без служебных полей самой записи (`id`, `createdAt`, `thumbId`), но со своими числами, временем,
источником, подписями и стоимостью.

Почему не позиции: строка и позиция это разное. У строки есть стоимость разбора, комментарий,
источник и связь с продуктом, у позиции ничего этого нет.

Альтернатива: при объединении делать из каждой строки без позиций одну позицию. Отклонена:
разбор по позициям возвращает строки без стоимости, без комментария и без связи с продуктом,
а запись из продукта после разбора перестала бы пересчитывать числа по весу.

Альтернатива: не разрешать объединение записей без позиций. Отклонена: владелец хочет
и объединять, и разбирать, и источник строки тут ни при чём.

### Составляющие плоские

При объединении каждая строка отдаёт свои составляющие, если они у неё уже есть, и себя саму,
если их нет. Вложенности не появляется: объединение объединённой записи с третьей даёт три
исходные строки.

Альтернатива: хранить объединённые записи целиком. Отклонена: разбор возвращал бы обратно
объединённую запись, и её пришлось бы разбирать второй раз.

### Разбор сначала смотрит на составляющие, потом на позиции

`splitEntry` возвращает составляющие, если их две или больше, иначе делит по позициям.
У строк время и дата свои: объединение их запомнило, и разбор возвращает их вместе со строкой.
У позиций время и дата берутся от записи: точнее мы его не знаем.

Восстановленная строка сохраняет свой источник. Иначе запись из продукта после разбора
перестала бы считаться по весу: формула правки опирается на источник и снимок значений на 100 г.

### Что делить, решает одна функция

`canSplit` отвечает на вопрос «есть что делить», а `entryParts` отдаёт составляющие для показа.
Ими пользуются и лента дня (решение открыть окно записи), и само окно (список и кнопка разбора).
Одно правило в одном месте: расхождение между лентой и окном и было видимой частью ошибки.

## Risks / Trade-offs

- Составляющие удваивают вес объединённой записи: каждая строка лежит и в записи, и в её
  составляющих. Записей в дне немного, а строки короткие, поэтому память не жалеем.
  Позиции, наоборот, в записи уже сложены, и второй копии не появляется.
- Старые объединённые записи разбираются по позициям, новые по составляющим. Разница видна
  только на записях, сделанных до правки.
- Снимок при разборе не переносится: как и раньше, он пропадает вместе с записью.

## Migration Plan

Данные не меняются и не переносятся: поле `parts` есть только у новых объединённых записей.
Откат: вернуть прежние `mergeEntries` и `splitEntry`, поле `parts` в записях никому не мешает.
