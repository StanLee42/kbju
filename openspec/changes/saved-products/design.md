# Design

## Context

Сейчас еда попадает в дневник двумя способами: ручным вводом в шторке правки и разбором
моделью, который открывается кнопкой «Добавить». Оба требуют ввода чисел: при ручном вводе их
набирают руками, при разборе их считает модель, а разбор стоит токенов.

В хранилище уже объявлен задел `dishes`, а в `js/tools.js` лежат инструменты `save_dish`
и `list_dishes`. Файл `js/tools.js` не импортируется ни одним модулем приложения, то есть задел
не подключён. Записи в `dishes` при этом никто не пишет.

Записи дневника хранят свои значения целиком. Модуль `js/portion.js` держит чистые функции
разбора и суммирования позиций, и его проверяют тесты. Модель уже отдаёт позиции с полем
`grams` и полем `basis`, которое объясняет, к чему отнесены числа.

Мотивация изменения изложена в `proposal.md`, требования - в `specs/saved-products/spec.md`.

## Goals / Non-Goals

**Goals:**

- Дать списку продуктов одно место хранения и одну точку входа.
- Вынести арифметику продукта в чистые функции, чтобы её проверял `node --test` без браузера.
- Не трогать разбор моделью: он остаётся способом завести новый продукт.

**Non-Goals:**

- Переделка окна разбора и карточки результата, кроме кнопки сохранения продукта и входа
  в список продуктов.
- Уборка мёртвого задела `dishes` и `js/tools.js`. Это отдельная работа.
- Единицы измерения кроме граммов: миллилитры, ложки и прочее.

## Decisions

### Отдельная возможность и отдельные модули

Список продуктов получает свою возможность `saved-products`, свой модуль расчёта и свою шторку.
Альтернатива состояла в том, чтобы встроить всё в `js/ui/add.js`. Она отвергнута: шторка ручного
ввода уже держит правку записи, и смешивать с ней список продуктов значит получить один модуль
с двумя разными моделями данных.

### Хранилище продуктов отдельное, версия хранилища поднимается

Вводится хранилище `products` с ключом `id`, версия базы поднимается с 3 до 4. Запись продукта
держит имя, значения на 100 г, счётчик использования и время последнего использования.

Альтернатива состояла в том, чтобы переиспользовать `dishes`. Она отвергнута по двум причинам.
Первая: контракт `dishes` другой, там значения отнесены к порции, а не к 100 г, и переиспользование
молча меняет смысл уже записанных полей. Вторая: задел `dishes` принадлежит не подключённому слою
ассистента, и связывать с ним новую возможность значит связать две несвязанные вещи.

### Единая точка входа, список живёт в окне «Добавить»

Отдельной кнопки для списка продуктов не заводится: кнопка «Добавить» остаётся одна. В её окне
сразу предложен разговор с моделью, а список сохранённых продуктов доступен оттуда же. Продукт
из списка можно добавить к результату разбора отдельной позицией, а можно записать в дневник
по весу, не обращаясь к модели.

Требование `food-chat` запрещает разделять ввод еды на отдельные способы. Разговор, снимок и
список живут в одном окне, поэтому требование выполняется: второго окна и второй кнопки нет.

Альтернатива: своя кнопка для списка на экране дня. Она отвергнута владельцем: кнопок ввода еды
должна быть одна, и человек не должен выбирать способ до того, как увидел окно.

Альтернатива: отдельная строка сохранённых продуктов в шторке ручного ввода. Она отвергнута
по той же причине, по которой у списка свой модуль: в шторке ручного ввода живёт правка записи,
и вторая модель данных там лишняя.

### Расчёт продукта выносится в чистые функции

Появляется модуль с двумя чистыми функциями: пересчёт набора значений на вес и пересчёт значений
разбора на 100 г. Вторая считается как отношение суммы значений к сумме граммов, умноженное
на сто. Поле `basis` при этом читать не нужно: у разбора с основой на 100 г граммовка позиций
уже равна ста, и отношение даёт те же числа.

Альтернатива состояла в том, чтобы разбирать каждый случай `basis` отдельно. Она отвергнута как
лишняя работа: арифметика отношения покрывает все три случая одним правилом, и тесты на неё короче.

### Запись из продукта хранит свои значения, а не ссылку

Запись дневника из продукта хранит посчитанные значения, вес порции, а сверх обычных полей
идентификатор продукта и снимок значений на 100 г. Правка веса пересчитывает запись по этому
снимку. Снимок лежит в своём поле записи: поля базовых значений в записи больше нет.
Ссылкой на живой продукт запись не ограничивается намеренно: иначе
правка продукта меняла бы прошлые дни, а этого требование не разрешает.

### Размер записи из продукта задаёт вес

У записи из продукта нет отдельного размера: числа считаются по весу порции и значениям
на 100 г.

### Порядок и поиск

Порядок по умолчанию - по счётчику использования, при равенстве по времени последнего
использования. Второй порядок - по алфавиту названий, он задаётся переключателем в списке.
Поиск идёт по вхождению части названия без учёта регистра.

Альтернатива: только алфавитный порядок. Она отвергнута, потому что регулярно едят несколько
продуктов, и они должны быть под рукой, а не в середине алфавитного списка. Алфавит оставлен
вторым порядком: он нужен, когда продуктов стало много.

### Название подсказывает сохранённые продукты

При вводе названия продукта под полем появляется короткий список сохранённых продуктов, название
которых начинается с введённых букв. В строке видны название и калории на 100 г. Касание строки
переносит название и значения на 100 г в форму, дальше их можно править. Совпадений нет,
подсказок нет.

Совпадение ищется по началу названия без учёта регистра, тем же правилом, что поиск в списке.
Совпадение по полному названию при сохранении по-прежнему обновляет существующий продукт.

Альтернатива: подсказывать по любому вхождению части названия. Она отвергнута: подсказки нужны
в начале набора, а вхождение даёт лишние строки в середине слова.

## Risks / Trade-offs

- **Продукт, сохранённый из оценки по снимку, наследует завышение.** Оценка порции по снимку
  завышена, это проверено на настоящих тарелках. Облегчение: числа упаковки помечены основой
  `label`, и выгодно сохранять продукты именно из упаковок. Источник чисел виден в карточке
  рядом с кнопкой сохранения: в строке под названием блюда сказано, взяты числа из таблицы
  на упаковке или оценены.
- **В одном окне сходятся путь без модели и путь с моделью.** Список и разговор живут вместе,
  поэтому рядом оказываются запись по весу без токенов и разбор с расходом. Облегчение: список
  показывает КБЖУ на 100 г сразу, запись по весу не отправляет запрос, а стоимость разбора
  видна отдельно.
- **В хранилище окажутся две сущности про еду.** `dishes` остаётся мёртвым рядом с живым
  `products`. Облегчение: это записано в `proposal.md` как отдельная работа, и удаление задела
  вместе с `js/tools.js` заводится отдельным изменением.
- **Счётчик использования ничем не ограничен сверху.** Это одно число на продукт, поэтому
  на обычную длину списка он не влияет. Если понадобится, счётчики можно сбросить отдельной
  правкой.

## Migration Plan

- Версия базы поднимается с 3 до 4, при обновлении создаётся хранилище `products`. Существующие
  хранилища и их данные не трогаются, обработчик обновления только добавляет недостающее.
- Переноса старых данных нет: писать в `dishes` было нечему.
- Откат: вернуть версию базы и убрать хранилище из списка. Записи в `products` при откате
  остаются в базе и не мешают, потому что версия ниже их не читает.
- Сборка публикуется как обычно: проверки идут при пуше, выпуск только из `main`.
