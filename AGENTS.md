# Правила работы с репозиторием KBJU

Файл читают и агент, и человек. Правила ниже уточняют общие правила из `~/.zcode/AGENTS.md`
и действуют только в этом репозитории. Подробный разбор подхода к спецификациям лежит в
`.misc/HOWTO_OPENSPEC.md` (каталог вне гита).

## Ветки

- `main` — план, документация и выпущенный код. В `main` попадает только проверенное.
- Работа идёт в своей ветке. Имя — по виду работы и краткому смыслу: `ai/<этап>` для этапов
  (так шли `ai/skeleton`, `ai/photo`, `ai/voice`), `feat/<имя>`, `fix/<имя>`, `docs/<имя>`
  для отдельных правок.
- Завершённая работа вливается в `main` через `--no-ff`, чтобы в истории оставался заметный
  merge-коммит.
- После вливания ветка удаляется и локально, и на `origin`: содержимое уже в `main`, а лишние
  ветки мешают.
- Отложенная работа в `main` не идёт и остаётся в своей ветке. Такую ветку не удаляют.
  Так живёт голосовой ввод в ветке `ai/voice`.
- Проверки запускаются при пуше в любую ветку, поэтому ошибку видно до вливания. Публикация
  идёт только при пуше в `main`.

## Коммиты

- Одна мысль — один коммит: отдельно спецификация, отдельно код (`feat`/`fix`), отдельно
  документация (`docs`), отдельно проверки.
- Заголовок: `<вид>(<область>): <что сделано>`, по-русски. Используется только дефис-минус.
- В теле коммита пишется причина и следствие, а не пересказ изменённых строк.

## Спецификации

- Сначала спецификация, потом код. Источник истины о поведении — `openspec/specs/`.
- Предложения лежат в `openspec/changes/`, завершённые переезжают в
  `openspec/changes/archive/` с датой в имени.
- Правила нормативного текста заданы в `openspec/config.yaml`: артефакты по-русски,
  структурные заголовки и ключевые слова SHALL/MUST по-английски.
- Блок `MODIFIED` заменяет требование целиком: сценарии, которых в нём нет, теряются.
  Поэтому перед архивацией обязателен `openspec validate --all --strict`.
- Пункт «проверка на телефоне» в задачи не пишется: владелец проходит по приложению сам
  после каждой правки. Проверки машиной и в браузере при этом остаются.

## Намерение и план

- Намерение пишется первым абзацем `proposal.md`, словами владельца: что не так и что хочется
  получить. Отдельный каталог `intent/` не заводится, чтобы не появился второй источник истины.
- План работы — шапка в `tasks.md` с четырьмя разделами: «Файлы», «Порядок», «Риски»,
  «Доказательство». Шапка нужна затем, чтобы правка не разошлась с планом молча.
- Если работа отходит от плана, план правится в том же коммите.
- Повторная ошибка становится тестом или правкой правил. Одного случая для этого мало.

## Проверки

Перед вливанием в `main`:

```
node --test                        # расчёты, разбор ответов, стоимость, порции, инструменты
openspec validate --all --strict   # формат спецификаций и предложений
```

После правок интерфейса или стилей дополнительно:

```
node tools/cdp-layout.mjs http://127.0.0.1:8766   # вёрстка и касания на 320–430
node tools/cdp-check.mjs http://127.0.0.1:8766    # страница и ошибки; печатает адрес сбойного файла
```

Сервер на 8765 отдаёт собранную папку `dist`, поэтому правки исходников проверяются на
сервере в корне репозитория (`python3 -m http.server 8766`).

Отчёт о готовности даётся только после прогона проверок, с их выводом. Если проверка упала,
сначала выясняется, что истина: код или проверка. По умолчанию правится код.

## Параллельная работа

- Каждая фича получает свою ветку и свой worktree: `git worktree add ../kbju-<имя> <ветка>`.
  Сессия открывается в каталоге worktree.
- Порт сервера у каждого worktree свой: 8766 займётся первым.
- Вливания в `main` идут по одному. Перед вливанием ветка подтягивает свежий `main`.
- Конфликты слияния разбирает агент. В отчёте он называет, что конфликтовало и как это решено.
- После вливания проверяется слитый результат, а не только ветка.
- Смысловой конфликт, а не текстовый, останавливает работу и требует решения владельца.

## Приватность

- Персональных данных владельца (вес, рост, возраст, состав тела) в репозитории быть не
  должно. В тестах, примерах и документации используется выдуманный человек.
- Ключ провайдера лежит в `.env.local` и в git не попадает. Сборка отдельно проверяет, что
  файлы с ключами не попали в `dist`.
- Каталоги `.misc/`, `spike/` и `dist/` в git не попадают.

## Что помнить в работе

- Оценка порции по снимку завышена: проверено на настоящих тарелках. На упаковках модель
  работает хорошо. Напоминать владельцу при работе над разбором еды.
- Голос и поиск в сети отложены решением владельца. Самостоятельно за них не браться.
- `cdp-update` в CI не добавлен (решение владельца, 2026-10-11). Вернуться к этому, если
  подхват новой сборки снова сломается.
